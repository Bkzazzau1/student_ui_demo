# E1 Development-Time Teacher Consensus

## Purpose

K-SLAS may use strong external foundation models during **development only** to help construct, review, and improve E1 training data.

Examples include:

- ChatGPT / OpenAI vision-capable models;
- Claude / Anthropic vision-capable models;
- Gemini / Google vision-capable models;
- Qwen, InternVL, and other suitable teacher/review models.

These systems are **teacher models**, not production exam models.

The live exam rule remains unchanged:

```text
live exam inference -> local K-SLAS edge AI only
```

No external teacher model is required, contacted, or trusted during a live examination.

## 1. What a teacher model does

A teacher model may help answer development-time questions such as:

```text
What object is inside this candidate region?
Is it phone, remote, book, or UNKNOWN?
Where does the visible object approximately lie in the full image?
Does this proposed annotation look plausible?
```

A teacher answer is **advice**, not ground truth.

Even if three teachers agree, K-SLAS still records that state as:

```text
teacher_agreement
```

not:

```text
human_approved_ground_truth
```

A human reviewer remains the final authority before the annotation enters the canonical E1 annotation-ingest path.

## 2. Why use several teachers

Different foundation models fail differently.

For example, a small rectangular object in a hand may be interpreted as:

```text
ChatGPT -> phone
Claude  -> remote
Gemini  -> unknown
```

That disagreement is useful information.

K-SLAS must preserve it instead of forcing a majority label.

The objective is not to ask, "Which AI is always correct?"

The objective is to use independent teachers to expose uncertainty before we train our own model.

## 3. Canonical vocabulary

Teacher responses must already use the frozen E1 canonical taxonomy.

### Base role

- `person`
- `phone`
- `laptop`
- `television`
- `keyboard`
- `mouse`
- `remote`
- `book`

### Specialist role

- `wrist_device`
- `earbud`
- `tablet`
- `paper_note`
- `calculator`

Teacher output such as `cell phone`, `tv monitor`, or another semantic alias is not silently converted by the consensus evaluator. `smartwatch` is retired under taxonomy `1.1` (replaced in place by `wrist_device`) and is likewise rejected rather than silently accepted as canonical.

The annotation workflow must resolve the class explicitly before ingest.

This preserves the same strict vocabulary boundary already enforced by `e1_annotation_ingest.py`.

## 4. Four teacher decisions

For each candidate object/region, a teacher must make one of four decisions.

### `canonical`

The teacher believes a supported canonical object is visible.

Example:

```json
{
  "decision": "canonical",
  "canonical_object_id": "phone"
}
```

### `no_object`

The teacher believes the candidate region does not contain a valid target object.

This is not the same as UNKNOWN.

### `unknown`

The teacher cannot make a defensible determination.

Examples:

- severe blur;
- heavy occlusion;
- tiny object;
- ambiguous object identity.

UNKNOWN must remain UNKNOWN.

### `abstain`

The teacher intentionally declines to judge the candidate, for example because the input is unsupported or unusable.

## 5. Candidate-based review

The first consensus tool evaluates **candidate regions** rather than independently matching arbitrary boxes generated by different teachers.

Why?

If three teachers independently produce three slightly different boxes, automatically deciding that they represent the same physical object requires a geometric matching policy such as IoU thresholds.

We have not scientifically calibrated such a threshold yet.

Therefore the current stage does not invent one.

Instead, a review packet identifies a candidate and asks multiple teachers to review that same candidate.

Each teacher may still return its own optional full-image normalized box.

Those boxes are retained separately.

They are **not averaged, fused, or treated as ground-truth geometry**.

A human reviewer resolves final geometry later.

## 6. Teacher packet format

The development-time schema is `1.0`.

Example structure:

```json
{
  "teacher_schema_version": "1.0",
  "packet_id": "e1-teacher-review-001",
  "model_role": "base",
  "image": {
    "image_path": "images/example/frame-0001.jpg",
    "width": 1280,
    "height": 720
  },
  "candidates": [
    {
      "candidate_id": "candidate-001",
      "teacher_votes": []
    }
  ]
}
```

The image path should be dataset-relative when real data is introduced.

Do not place participant identity in the path or candidate ID.

## 7. Teacher identity and model provenance

Every vote records:

- `teacher_id` — stable workflow identity for that teacher configuration;
- `provider` — for example `openai`, `anthropic`, or `google`;
- `model_id` — the exact model identifier actually used for that response;
- `decision`;
- canonical label when applicable;
- optional normalized geometry when applicable.

Do not write a guessed model name.

When we begin actual API/manual teacher runs, record the exact model identifier returned/configured at that time.

## 8. Consensus states

The evaluator produces the following review states.

### `teacher_agreement`

At least two independent teacher providers supplied effective decisions and all effective decisions agree, with no UNKNOWN vote.

This is still not ground truth.

### `needs_human_review`

Examples:

- teachers disagree;
- any teacher returns UNKNOWN;
- different canonical classes are proposed.

### `insufficient_review`

Only one provider is represented.

Multiple model calls from the same provider do not pretend to be independent multi-provider consensus.

### `unresolved`

No effective decision remains, for example all teachers abstain.

## 9. No confidence voting

The consensus evaluator does **not** weight teacher self-reported confidence.

A response such as:

```text
phone, confidence 0.99
```

is not automatically more authoritative than another teacher saying:

```text
remote, confidence 0.61
```

Foundation-model confidence values are not calibrated K-SLAS probabilities.

The current evaluator therefore ignores confidence fields rather than creating false mathematical precision.

## 10. No automatic geometry fusion

Teacher bounding boxes remain separate.

The system does not currently:

- average boxes;
- choose the highest-confidence box;
- invent an IoU threshold;
- convert teacher geometry into final annotation geometry.

If a teacher supplies geometry, it must use:

```text
bbox_xywh_normalized = [x, y, width, height]
```

against the original full image.

The human-approved annotation later enters `e1_annotation_ingest.py`, where the existing geometry contract applies.

## 11. Provider-neutral teacher prompt

When the same candidate is sent to ChatGPT, Claude, Gemini, or another teacher, use the same semantic instruction.

Recommended development prompt contract:

```text
You are acting only as an offline development-time annotation teacher for K-SLAS E1.
You are not making a misconduct decision.

Review the supplied image/candidate region and return exactly one decision:
canonical, no_object, unknown, or abstain.

If canonical, choose only from the supplied E1 canonical class list for this model role.
Do not invent aliases or new classes.
If the object is ambiguous, use unknown.
Do not infer an object from hand pose or context alone.
If you provide a bounding box, express it as full-image normalized [x, y, width, height].
Do not infer hidden or occluded geometry beyond what is visually defensible.
```

The actual transport/API wrapper may add machine-readable response formatting, but must not change these truth rules.

## 12. Example: phone candidate

Suppose the candidate contains a real phone.

```text
OpenAI teacher     -> phone
Anthropic teacher  -> phone
Google teacher     -> phone
```

The evaluator returns:

```text
teacher_agreement
suggested_decision = phone
human_review_required = true
```

The human reviewer still confirms the class and final bounding box.

## 13. Example: remote hard negative

```text
OpenAI teacher     -> remote
Anthropic teacher  -> remote
Google teacher     -> remote
```

This helps establish the important distinction:

```text
remote != phone
```

Again, teacher agreement is only a review aid.

## 14. Example: ambiguous object

```text
OpenAI teacher     -> phone
Anthropic teacher  -> remote
Google teacher     -> unknown
```

The correct system response is:

```text
needs_human_review
```

not majority vote.

This sample can later become:

- human-approved `phone`;
- human-approved `remote`;
- excluded from training;
- retained as a difficult review case.

The human decision must be explicit.

## 15. Running the evaluator

From the repository root:

```powershell
python -m ai_runtime.e1_teacher_consensus --pretty data/teacher/e1_packet.json data/teacher/e1_report.json
```

The output is a **human-review report**, not an E1 training manifest.

Existing output is protected unless `--force` is explicitly supplied.

A synthetic format example is available at:

```text
docs/edge_ai/examples/e1_teacher_consensus.example.json
```

It contains no real participant data and is not training evidence.

## 16. Development workflow before real K-SLAS data

We can use synthetic/example images and teacher-response fixtures now to validate the workflow:

```text
synthetic/example image
    -> candidate region
    -> ChatGPT teacher response
    -> Claude teacher response
    -> Gemini teacher response
    -> provider-neutral teacher packet
    -> e1_teacher_consensus evaluator
    -> agreement/disagreement report
    -> human review exercise
```

This lets us debug the annotation methodology without pretending synthetic examples are production evidence.

## 17. Workflow once real data arrives

Later:

```text
real retained K-SLAS frame
    -> candidate generation / annotation task
    -> multiple development-time teacher reviews
    -> consensus report
    -> human approval
    -> canonical annotation staging
    -> e1_annotation_ingest
    -> dataset readiness gate
    -> source-group-safe train/validation/test datasets
    -> training
```

The teacher systems disappear completely from the live exam runtime.

## 18. Hard rules

1. External teachers are development-only.
2. No external teacher is required during a live exam.
3. Teacher agreement is not ground truth.
4. Human review is required before canonical training annotation.
5. UNKNOWN is preserved.
6. Teacher disagreement is preserved.
7. Canonical E1 classes only.
8. No semantic alias guessing.
9. No teacher-confidence weighting.
10. No automatic teacher-box fusion at this stage.
11. No invented geometric matching threshold.
12. No misconduct conclusion is produced by the annotation teacher workflow.
13. Exact teacher provider/model provenance must be recorded when real teacher calls begin.
14. Synthetic examples remain explicitly synthetic and are never reported as real training evidence.
